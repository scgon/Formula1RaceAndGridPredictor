## Environment

- **Interpreter**: `/opt/homebrew/Caskroom/miniconda/base/bin/python` (Python 3.14, all deps installed). Do NOT rely on `python3` from PATH — on a fresh shell it can resolve to macOS system Python, which has none of the packages. PyCharm uses this same miniconda SDK.
- **GitHub CLI**: `/opt/homebrew/bin/gh` (authenticated as `scgon`); often not on PATH.
- **Feature worktrees**: new features are usually developed in sibling git worktrees (`git worktree add ../Formula1RaceAndGridPredictor-<name> -b <branch>`). A worktree checks out its own tracked `data/*.csv` (bundled seasons need no re-download) but starts with a **cold fastf1 cache** — `cache/` is gitignored. To share the main checkout's ~1 GB of downloaded sessions, symlink it: `ln -s <main-repo>/cache cache`. Gotcha: a `cache` *symlink* shows as untracked in `git status` (the `cache/` ignore pattern matches directories only) — never `git add -A` over it; drop the symlink when the worktree is retired.
- No tests, lint, or typecheck exist. Verification = a full script run (pipelines), an AppTest run (web app), or a CLI-output parity diff (pipeline edits).

Page scripts and `webapp_common` self-bootstrap `sys.path` (`webapp/` + `pipelines/`), so they run from the repo root without installation; `app.py` needs no bootstrap (imports only streamlit). `f1_common.BASE_DIR` points at the repo root, so `cache/` and `data/` are shared by pipelines, web app and notebooks no matter where each is executed from.

**Stale-module guard**: every page calls `webapp/_bootstrap.fresh_modules()` right after its path bootstrap. Streamlit Community Cloud pulls new commits into the *live* app process without restarting the interpreter ("Updated app!" — no "Starting up repository"), so page scripts re-execute from the new source while `sys.modules` keeps serving the pre-pull modules — the extras commit's first deploy crashed exactly this way (`AttributeError: module 'webapp_common' has no attribute 'run_extras_pipeline'` in a process up since the previous evening, while race/quali pages kept working because their module API was unchanged). `fresh_modules` compares each module's source file (mtime, size) against the stamp recorded at the last verification and `importlib.reload`s the whole chain in dependency order on drift (stamped in `MODULES`: f1_common → the three pipelines → webapp_common), so the app self-heals on the first rerun after a code pull; reloads keep `@st.cache_resource` hits intact (Streamlit hashes `__module__`+`__qualname__`, not object identity). Gotcha: `_bootstrap.py` itself cannot self-heal (the running guard would already have to be the new version) — keep it tiny, stdlib-only and stable.

## Commands

```bash
PY=/opt/homebrew/Caskroom/miniconda/base/bin/python

$PY -u pipelines/predict_race.py   # race prediction (gain + direct models; direct-only before quali)
$PY -u pipelines/predict_grid.py   # qualifying/grid prediction (anchor + direct models)
$PY -u pipelines/predict_extras.py # milestone pick — one model per run (--milestone selects it)
$PY -m streamlit run app.py        # web app (homepage + one page per pipeline)
$PY scripts/refresh_data.py        # refresh the bundled season CSVs (default: previous + current season)
                                    # bulk-generate seasons: --years 2018 2019 ... --wait-on-limit
```

Shared CLI flags: `--season YEAR`, `--predict-round N`, `--next` (next race/quali on the calendar), `--refresh` (re-download season data), `--min-train-rounds N`, `--model {fast,optimized}` (model profile, see below), `--models` (which models the race/quali pipeline trains — `both` (default), `gain`/`anchor`, or `direct`; a pre-quali race target always falls back to `direct`), and the output-level pair `-q/--quiet` + `-v/--verbose` (see the verbosity bullet in Architecture).

- **A bundled season's first run downloads nothing but newly completed rounds** (the season CSVs are tracked in the repo); an unbundled season's first run downloads ~45 fastf1 sessions (several minutes). After that `cache/` and `data/*.csv` make runs take ~3-4 min. A round that fails mid-download is skipped and retried on the next run.
- Always run with `-u`; do not pipe output through `head` — block buffering makes long jobs look stalled.
- Under system load (e.g. a PyCharm Jupyter kernel is running), cap threads: `OMP_NUM_THREADS=4`.

## Architecture

- `pipelines/f1_common.py` — shared machinery for all three pipelines and the web app: fastf1 cache setup, UTC/session-time helpers (`utc_now`, `session_utc`, `completed_rounds`), quali-lap extraction (`best_quali_seconds`, `pole_seconds`), practice-lap features (`practice_features(year, rnd, sessions)`), the season CSV cache (`collect_season`, parameterized by filename/columns/result column/loader, with a soft stop on the F1 API rate limit and an optional `rate_limit_wait` sleep-and-retry), the model factory, `rank_corr`, permutation importance (`importance_scores` returns a DataFrame, `importance_report` prints it) and the CLI verbosity gating (`VERBOSITY`, `vprint`, `add_verbosity_args`/`apply_verbosity`).
- **Verbosity** — the module-global `f1_common.VERBOSITY` gates CLI output; `-q/--quiet` (0) trims runs to the backtest summary + final prediction (no progress lines, per-round backtest table or importance), `-v/--verbose` (2) adds live per-round backtest result lines, hyperparameter-tuner decisions (`tuner: adopting ... (pooled ...)` / `tuner: keeping fast hyperparameters ...`), importance `±std` spread and the full extras probability table; default (1) is exactly the historical output. `add_verbosity_args(parser)` / `apply_verbosity(args)` wire the mutually-exclusive flags; progress prints go through `vprint(level, ...)`, reports gate sections on `VERBOSITY`. The web app never calls `apply_verbosity`, so it always runs at level 1 — its live download/training log (which relies on the progress prints) is unaffected.
- **Model profiles** — the CLI `--model {fast,optimized}` flag and the web-app *Model profile* selectbox select between: `fast` (default) — `HistGradientBoostingRegressor` with the fixed `FAST_PARAMS`; `optimized` — before every fit, `f1_common.tune_hyperparameters` runs a seeded randomized search over `TUNED_SEARCH_SPACE`, scoring candidates by pooled MAE over rolling CV folds (each fold = one training round predicted by the rounds before it; `TUNE_MAX_SPLITS` recent rounds, `None` + `TUNE_STRIDE` = strided leave-one-round-out). `FAST_PARAMS` is always the first candidate, ties keep it, and a candidate must beat it by `TUNE_MIN_IMPROVEMENT` (relative MAE) or the tuner returns `None` and the fit falls back to the fast values (this also covers <2-round training sets, so degenerate single-round models behave identically under both profiles and the web-app degenerate notes stay accurate). Tuning inside the backtest only ever sees rounds before the predicted round, so optimized backtest metrics stay honest. A fold's training share can be all-NaN in a column (round 1 has no form/sprint data) — the tuner zeroes those columns for that fold (a constant column can't be split on); without that, HistGB raises and the backtest silently skips the round. `train_model` returns the tuned dict; `final_predictions` bundles it as `gain_params`/`anchor_params`/`direct_params` for the CLI/web-app "Tuned hyperparameters" display. **The web app hides the optimized profile on Streamlit Community Cloud** (`webapp_common.on_community_cloud` — every Community Cloud app is served at a `*.streamlit.app` URL, so `urlparse(st.context.url).hostname.endswith(".streamlit.app")` detects it; the API exists since Streamlit 1.45, covered by the `>=1.55` pin, and fails open to False when the URL is unavailable, e.g. `None` under AppTest): `model_profile_input` then offers Fast only, with a caption pointing local users to the full choice — its multi-minute tuning searches would hog the shared cloud container. Local runs, AppTest and the CLI keep both profiles.
- Two **independent pipeline entry points** — `predict_race.py` (gain = finish − grid vs direct = absolute finish; baseline = grid order) and `predict_grid.py` (anchor = change vs last quali vs direct; baseline = last-quali persistence). Each owns its FEATURES/targets/feature engineering (`build_features`), sprint handling and round loaders.
  - **Race target modes** (`resolve_target` returns (round, mode, event)): `post` reviews a completed round; `pre` predicts after qualifying (grid known — `load_upcoming_round` builds the frame from quali results); **`prequali`** predicts before qualifying — no grid exists, so `load_upcoming_round_prequali` builds the frame from practice entrants (first session with results, else the last completed round's entrants), grid/quali features stay NaN, and `final_predictions(..., models="direct")` runs the **direct model only** (the gain model has no grid to anchor to; HistGB routes the NaN grid at inference down the learned missing-value branch). Auto/`--next`/`--predict-round` all resolve an upcoming round to `prequali` when its quali hasn't run — with a printed note when no practice has finished yet (`practice_done_by`, 2h buffer). The backtest skips rounds with no grid rows entirely (nothing to anchor to or score); rounds with a grid keep byte-identical behavior.
  - **Grid information set**: FP1/FP2 pace always, plus sprint quali, **FP3** (`fp3_*` columns) and **sprint-race results** (`sprint_finish`/`sprint_gain`) when those sessions have already run — never mandatory: they are NaN before they happen (sprint weekends have no FP3; non-sprint weekends have no sprint race), `usable_features` drops them only when a training set has none at all, and HistGB handles the rest. This replaced the old day-before-quali constraint; the backtest therefore evaluates the "everything available pre-quali" task, and pre-mode predictions made Friday just carry NaN for the Saturday-morning features.
- Each pipeline exposes structured results alongside the printed reports, for the web app:
  - `backtest_records(features, min_train_rounds, profile, models="both")` → list of per-round metric dicts; `backtest_report(records, models)` prints it. `models` (the CLI `--models` flag; the web app always uses the default) selects what trains per round — `both` (default), `gain`/`anchor` or `direct` — and records then carry only the trained model's fields alongside the shared baseline/actual fields, so single-model CLI runs print single-model columns; `both` records are unchanged. The record/report split left CLI output text unchanged; `backtest_records`/`final_predictions` have since gained live per-model training-progress prints (see the web-app execution bullet below). Records also carry web-app-only fields the CLI never prints: `gain_points`/`direct_points` (race podium scoring: +15 exact position, +5 wrong slot) or `anchor_points`/`direct_points` (grid pole scoring: +15 correct pole), `*_top1` and `actual_top1` winner/pole driver names, and `*_train_rounds` (rounds each model trained on — a value <2 means the model degenerates to the baseline order, see below).
  - `final_predictions(features, target, profile, models="both")` → the selected models' keys only (`{"gain"/"anchor", "direct", "*_model", "train", "*_features", "*_params"}` for `both`); `final_report(..., models)` prints it. With both models the main frame carries a `direct_pos` column for side-by-side display; a race `prequali` target passes `models="direct"` (no grid to anchor to — `--models gain` there prints a note and falls back). Gotcha: with both models the grid bundle's `train` frame stays the ANCHOR's training set (the direct set is a superset that includes round-1 rows with NaN `quali_pos_last`, which would crash the anchor importance target) — direct-only runs use the direct set. The `*_features` lists are the features each model actually used (all-NaN training columns dropped, see below); the `*_params` dicts are the hyperparameters the profile picked (None = fast defaults).
  - `importance_frame(pred, mode)` → permutation-importance DataFrame for one final model.
- sklearn's `HistGradientBoosting` **cannot fit a feature column that is entirely NaN** — it raises `ValueError: window shape cannot be larger than input array shape` (still true in sklearn 1.9.x; round-1 rows have all-NaN form features, sprint columns are all-NaN before the first sprint weekend). Each pipeline's `train_model` therefore drops those columns via `usable_features(train)`, `make_model(feature_names)` computes the `team_id` categorical index within the reduced list, and `predict_round`/importance reuse the returned feature list. Rounds with a full training set are unaffected, so default CLI output is unchanged; this is what makes the race backtest able to predict round 2 (trained on round 1 only).
- A model trained on a **single round (~22 rows) cannot make any tree split** (`min_samples_leaf=20` needs ≥40 rows in a parent), so it predicts a constant and its "prediction" collapses to the baseline order (grid order for race — a constant gain added to grid; last-quali order for the grid pipeline — a constant added to the anchor, plus `rank(method="first")` tie-breaking by the grid/driver pre-sort). This affects race round 2 and quali round 3; their backtest rows/metrics are baseline performance, not model skill. The web app flags this via `degenerate_backtest_note` / `degenerate_training_note` (webapp_common), gated on the `*_train_rounds` record fields and the bundle's `train_rounds`.
- `pipelines/predict_extras.py` — the **milestone pipeline**: seven small binary `HistGradientBoostingClassifier`s (one per target in `TARGETS`: pole, winner, podium, first_dnf, fastest_lap, sprint_pole, sprint_win), each with its own feature list — **one runs per invocation**, selected with the CLI `--milestone` flag or the web-app *Milestone* selectbox (default pole). The selected model scores every driver of the target round with `predict_proba`; top pick = prediction, compared against naive baselines (pole: best season quali form, winner: grid P1, podium: grid P1, first DNF: most retirements, fastest lap: most FLs then fastest qualifier, sprint pole: best previous sprint-quali form then season quali form, sprint winner: the sprint pole sitter — `baseline_pick` sorts by `TARGETS[name]["baseline_sort"]`, NaN last, driver_number tie-break).
  - **Information sets**: the pole model keeps the day-before-quali information set the grid pipeline originally used (FP1/FP2 → stored as `fp12_*` columns, sprint quali, quali form, points — the grid pipeline itself has since relaxed to optionally include FP3/sprint race); the four race-milestone models mirror the race pipeline's pre-race set (grid, FP1–FP3 `fp_*`, sprint quali + sprint race, driver/team form, points) plus reliability/milestone history (`driver_dnf_rate_season`, `team_dnf_rate_season`, `driver_wins_before`, `driver_fl_before`, `driver_podiums_before`, …) — all `shift(1)`-derived in `build_features` like the other pipelines. The sprint models respect sprint-weekend chronology (FP1 → sprint quali → sprint race → GP quali → race): **sprint_pole** trains/predicts on FP1, quali form and past-sprint history (`sprint_quali_pos_last`, `sprint_quali_form_season`, `sprint_finish_last` — built with a shift over each driver's non-null sprint entries, so weekend N never sees its own results), while **sprint_win** may additionally use the target round's sprint quali result but never the sprint race results or GP quali.
  - **Sprint milestone details**: the two sprint targets are DERIVED in `build_features` from the stored `sprint_quali_pos`/`sprint_finish` columns (`sprint_pole = SQ P1`, `sprint_win = sprint P1`) — no CSV schema change, no regeneration. Both models train only on sprint rounds (`train_columns` masks on `sprint_quali_pos`/`sprint_finish`) and score the sprint-quali participants of the target round (`rows_column="sprint_quali_pos"`); a round with no eligible candidates (any non-sprint weekend) is skipped by the backtest and makes `final_predictions` return a "no ... candidates (sprint weekends only)" error, which the page renders as a warning. Training sets are tiny (~5-6 sprint rounds per season) — degenerate-caption wording and the fast-fallback tuner behavior apply as for the other classifiers.
  - **Own season CSV** `extras_season_{year}.csv`: the first-retirement and fastest-lap targets need **race lap data** (`race.load(laps=True)`), which neither other pipeline downloads, so the extras loader re-derives everything itself into one self-contained frame (quali/race/FP/sprint sessions come from the shared fastf1 cache). Bundled for **2025–2026** only; the web-app season picker therefore calls `bundled_years("extras")` (extras page offers only years with an extras CSV — keep this gating if the data coverage changes), the CLI stays unrestricted. First cold collection of a season costs ~25–30 API calls per round (lap data counts against the 500/hour limit) — expect a rate-limit soft stop mid-season and resume by re-running.
  - **Target definitions**: pole = quali P1; winner = race P1; podium = classified finish in the top three (`finish <= 3`, DERIVED in `build_features` from the stored finish column like the sprint targets — no CSV schema change; DNS rows are NaN and never podium); a driver retired (`dnf`) iff `finish` is not NaN (DNS rows are NaN) and the status is not Finished-like (`Finished`, `Lapped`, `Disqualified`, `+N Lap(s)` — DSQ completed the race, so it is not a retirement); `first_dnf` = the retiree(s) with the fewest completed laps (min lap count; lap-1 pile-ups tie → multi-hot set, a hit is any of them, backtest hit rates average only over rounds with ≥1 retirement — `dnf_any` records which those are); `fastest_lap` = min race `LapTime` (deleted laps filtered).
  - **Pre-race / pre-quali modes**: the extras pipeline resolves targets like the race pipeline's pre mode (pre requires quali done, so the upcoming frame always has a grid), so in pre mode every milestone flagged `pre_scored` in `TARGETS` (pole, sprint_pole, sprint_win — all decided before the race on a 2026 sprint weekend: SQ Friday, sprint Saturday morning, GP quali Saturday afternoon) is immediately scoreable — `load_upcoming_round` merges the quali results and the sprint quali/race results, so `actual_drivers` knows those milestones but not the race milestones (their flags are 0 → `actual=[]` → hit `None` → displayed as "not known yet"); the backtest's last round likewise scores the pre_scored milestones but has NaN race-milestone hits. The **pole model additionally has a prequali mode** (`TARGETS["pole"]["prequali"]`): its feature set never includes the target round's qualifying, so when the pole milestone is selected an upcoming round whose quali hasn't run resolves to `prequali` — auto/`--next`/`--predict-round` all do this, while the race milestones keep requiring quali (old messages, and auto still falls back to the last completed round). `load_upcoming_round_prequali` mirrors the race pipeline's: entrants from the first practice session with results (else the last completed round's entrants), quali columns NaN, `pole` flags 0 → unknown ("not known yet"), with `practice_done_by`/`_prequali_note` printing the no-practice-yet note. `target_rows` falls back to all entrants when no row has a `rows_column` value, the milestone's spec sets `prequali` and the round has no quali positions at all (previously that case crashed `baseline_pick`; completed candidate-less rounds — a non-sprint weekend for the sprint models — still return empty and surface the "sprint weekends only" error). The prequali round rides along as the backtest's last row with NaN hits, exactly like pre-mode race-milestone rows — the sprint branch's skip of candidate-less rounds therefore only drops *completed* rounds (a prequali target has no `finish` yet); post/pre output stays byte-identical. `webapp_common.resolve_target` threads the selected `milestone` into the extras namespace (race/grid ignore it).
  - **Sprint models before qualifying**: the sprint sessions happen before GP quali, so `sprint_pole`/`sprint_win` also carry `prequali: True` and predict an upcoming sprint weekend before its quali runs (`_upcoming_quali_mode`) — SQ results merge into the prequali frame once SQ has happened, so a post-SQ sprint-pole call is already scored, a post-sprint-race sprint-winner call too. Sprint-milestone resolution is sprint-gated (`is_sprint_weekend`, from the schedule's Session names "Sprint"/"Sprint Qualifying"): `--next`/`--predict-round` on a non-sprint upcoming round exits with a hint at the next sprint weekend; auto jumps to the next upcoming sprint weekend, and with none left it reviews the last completed *sprint* round (`data["sprint_quali_pos"].notna()`). The web-app *Target weekend* selectbox (`webapp_common.target_selectbox(..., milestone)`) accordingly lists only sprint weekends for the sprint milestones, and offers "Next on the calendar" only while the next upcoming round is one.
  - **Classifiers ≠ regressors**: `CLASSIFIER_FAST_PARAMS` = FAST_PARAMS minus `loss` with `min_samples_leaf=10` (positives are ~1/20 of rows); the tuner is the local `tune_classifier` (same folds/sampling/min-improvement as `f1_common.tune_hyperparameters` but scoring pooled **log loss**; single-class training folds are skipped, a single-class training set raises `ValueError` in `train_model` → that round records NaN metrics instead of crashing); permutation importance uses `neg_log_loss`. A single-round-trained classifier CAN split (min_samples_leaf=10 fits ~20 rows), so the extras page uses its own softer degenerate captions rather than the "reproduces the baseline order" wording. `backtest_records(..., milestone)` / `final_predictions(..., milestone)` run only the selected target: records carry flattened per-round fields (`hit`/`top3`/`base` for the model pick, top-3 and baseline, `top1`/`baseline`/`actual` names, plus `pick_proba`/`actual_proba` — the probabilities the model gave its own pick and the actual driver, charted on the page), and `final_predictions` returns a single entry (`pred["name"]` holds the milestone key, `train_rounds` inside; an `"error"` key replaces the model when it cannot train). `webapp_common.run_extras_pipeline(..., milestone)` mirrors `run_pipeline` with that single-model bundle (`pred`/`imp`, `milestone`, settings tuple includes the milestone so switching it triggers the "settings changed" warning).
- **Streamlit app** (`app.py`, `st.navigation`): `webapp/page_home.py`, `webapp/page_race.py`, `webapp/page_quali.py`, `webapp/page_extras.py` are the pages (`st.Page` and `st.page_link` paths resolve relative to `app.py`, i.e. the repo root); `webapp/webapp_common.py` is app-only glue (no pipeline logic): `capture_stdout` (optionally streams printed output live into an `st.empty` log element), `run_pipeline` (data load → target resolution → features → backtest → final models → importance, returns a render bundle or `{"error": ...}`; for a race `prequali` target it passes `models="direct"`, renders the direct frame as `main` and sets `imp_main` to None) / `run_extras_pipeline` (same flow for the milestone pipeline), and small UI/table/chart helpers. `webapp_common.page_link` wraps `st.page_link` so pages also run standalone (AppTest) where no navigation context exists.
- Web app execution model — **button-gated**:
  - Changing a widget never starts the pipeline. The sidebar **Run prediction** button executes `run_pipeline` once and stores the bundle in `st.session_state[f"{kind}_result"]` (plus a settings snapshot used for the "settings changed since the last run" warning); every rerun afterwards just renders from the bundle.
  - **Reload season data** bumps `st.session_state[f"{kind}_data_version"]` and refreshes the data layer only (with live progress in a log element). The **Force full re-download** checkbox maps to CLI `--refresh` but takes effect only on the next Reload/Run press — checking it alone downloads nothing.
  - Only `team_colors` is `@st.cache_resource`-cached (tiny, element-free) — never create Streamlit elements inside cached functions (CacheReplayClosureError); the uncached collect path is exactly what allows the live download log. `get_schedule` is deliberately NOT Streamlit-cached: `@st.cache_resource` pins the schedule frame for the whole process lifetime, and the hosted process outlives code pulls — the cloud app once served a pre-correction schedule that gated Singapore's sprint milestones off with "not a sprint weekend" for days while local runs (fresh process each time) were fine (see the schedule gotcha below). It instead keeps a module-level TTL cache (`SCHEDULE_TTL`, 12h, aligned with fastf1's own HTTP-cache expiry for the schedule): an aged entry is re-fetched (one tiny API call), a failed refresh serves the last good copy and retries on the next rerun, and it raises only with no copy to fall back on. A `fresh_modules` reload resets the dict, so each deploy re-fetches once. `collect_season` prints `fetching round N  <event> ...` before each round download so users can track slow progress, and `backtest_records` / `final_predictions` print one line per model being trained (`backtest round N  <event>: training gain model...`, `training final direct model (tuning hyperparameters)...`) — `run_pipeline` keeps the whole run inside one `capture_stdout(log_box)` so both kinds of progress stream live into the same log element.
- Web app presentation details:
  - Tables keep **numeric underlying values** and display `P{n}` via pandas Styler formats, so interactive column sorting is numeric (not the "P1, P10, P11" string sort). Cell colors are Styler CSS: gold/silver/bronze for P1/P2/P3 cells (`position_css`), green for exact predictions (`zero_error_css` on the error columns in review mode), a blue heat-map over the extras page's Probability column (`probability_css` — fill opacity tracks the probability; the text color is fitted for contrast against the fill *blended over the theme background*. Dark mode uses a lighter fill — `PROBABILITY_FILL_DARK` — with a stronger, gamma-stretched opacity ramp, and flips the text to dark navy on the rare cell bright enough that no light color reaches 4.5:1 with it: the light-mode blue kept translucent over the near-black theme background stayed within ~1.5:1 of it at the probabilities these models actually produce (top picks ≈20–40%), so the heat map was invisible in dark mode. Light mode is the original pastel ramp with navy text, byte-identical), team-colored Driver/Team text — **every driver and team name on every page renders in its team's color**: the Driver *and* Team columns of all three prediction tables go through one shared helper, `style_driver_team_columns(styled, frame, colors)` (the Driver column resolves each driver through the source frame's own driver/team pairing via `team_by_driver` — a frame-level driver→team map, last row wins — and the Team column colors by its own team-keyed value; the race/quali pages used to pass the Driver cell straight into the team-keyed color map and the extras page made the mirror mistake on the Team column, so one column per page silently fell back to gray). Driver names inside `st.success`/`st.info` boxes (podium/pole/milestone/actual callouts) are colored by `driver_md`/`drivers_md`, which emit `:color[VER]{foreground="#hex"}` markdown directives — alert boxes escape raw HTML, but the custom-color directive is processed at the markdown AST level and renders inside them (needs `streamlit>=1.55`, pinned in requirements.txt; boldness stays under the caller's `**...**`). The extras top-10 probability chart is `probability_chart` (Altair, rendered with `st.altair_chart(theme="streamlit")`): native `st.bar_chart` colors every bar alike, so it mirrors the lane diagram's team-color scale, one bar per driver. Team colors: `team_colors(year)` (`@st.cache_resource`, `ttl=3600`) reads the **bundled `data/team_colors.csv`** (year, team, color — one raw fastf1 row-set per season, written by the refresh script's `refresh_team_colors` from `f1_common.season_team_colors`) first, so a fresh app container renders colors with **zero fastf1 API calls**; only years the bundle doesn't cover (e.g. a next-season preview) fall back to a live latest-completed-round `TeamColor` lookup, and a failed fallback degrades to gray instead of raising. The bundle exists because the original live-only lookup broke the hosted app: on Community Cloud the fastf1 cache is cold and the 500-calls/hour budget is per *process*, so once data downloads exhausted it, `session.load` raised inside `team_colors`, the swallowed exception collapsed the map to `{}`, and `@st.cache_resource` **pinned that all-gray map for the rest of the process lifetime** (which survives code pulls for days). The `ttl` now also bounds how long any live-path failure can stick. After reading (either source) `expand_team_aliases` adds every historical name from `TEAM_LINEAGES` — the season CSVs carry old constructor names (`Alpine F1 Team`, `RB F1 Team`, `Red Bull`, `Sauber`, ...) while fastf1 uses the current name (`Alpine`, `Racing Bulls`, `Red Bull Racing`, `Kick Sauber`), mixed within one season, so without the expansion those rows silently fall back to gray (when a team renames again, add its names to `TEAM_LINEAGES`; the bundle stores only the raw fastf1 names, so new lineage entries retro-apply on read). `readable_color` is theme-aware: colors already at WCAG-AA contrast (4.5:1) pass through unchanged, the rest keep hue/saturation but get darkened on light backgrounds and brightened on dark ones (`theme_is_dark` reads `st.context.theme`, re-evaluated every rerun, so toggling the theme recolors on the next rerun); the lane-diagram driver codes, the box directives, the probability bars and the cut lines all go through the same adjustment. Keep `LIGHT_BACKGROUND`/`DARK_BACKGROUND` in sync with the actual theme backgrounds if a `.streamlit/config.toml` is ever added.
  - **Display frames are `reset_index(drop=True)` copies, but the pipeline frames they copy from keep the season frame's row labels** (e.g. 330–351 for a late-season round). Assigning a Series into a display column aligns *by label*, so every cell silently lands NaN and the column renders blank — the extras Achieved column shipped exactly this bug (fixed; nobody was ever marked "yes"). Populate display columns positionally with `.to_numpy()` (the race/quali pages' `Actual`/`Error` columns do); same-frame ops like `picks["Hit"] = ...` on a bt-derived frame are unaffected.
  - In review (post) mode the prediction table is sorted by the actual result; in prediction (pre/prequali) mode by the gain/anchor prediction. A race prequali target renders a direct-model-only table (no Gain/Grid columns), a single-lane order diagram, one podium box and one importance chart.
  - The sidebar "First backtest round" selectbox maps to `min_train_rounds` (completed rounds are calendar-based, no data load needed). Its default, **Auto (recommended)**, passes the pipeline default `MIN_TRAIN_ROUNDS` (5); an explicit round maps to the count of completed rounds before it. Earliest explicit round: 2 for race and extras (round 1 can never be predicted — no training data before it), 3 for qualifying (the anchor model additionally needs each driver's previous quali result).
  - Charts are Streamlit-native (no matplotlib): the prediction-error-by-round chart is a `st.bar_chart(..., stack=False)` grouped series; the "final predicted grids" lane diagram (`predicted_order_chart` in webapp_common) is an Altair layered chart rendered via `st.altair_chart(..., theme="streamlit")` — the same engine/theme as native charts, used because text marks and dashed cut rules aren't expressible with the `st.*_chart` shortcuts. Lane order (bottom → top): gain/anchor model, direct model, actual result / starting (or last-quali) grid — keep the page captions in sync. Gotcha: an Altair y-axis `sort` array lists categories **top → bottom** (verified against the compiled Vega spec) — `predicted_order_chart`'s `rows` param is bottom → top and gets reversed into the sort, while `probability_chart` passes its probability-descending table straight through so the top pick lands on the top bar; don't flip either. Cut lines: race podium/points (3.5 / 10.5); quali Q3/Q2 (10.5 / 16.5 — with the 22-car grid, P16 reaches Q2). The extras page's top-10 probability bar chart is the same kind of Altair chart (`probability_chart`, team-colored bars — see the presentation bullet above). The race/quali pages also show podium/pole points and predicted winner/pole tables, each with bold **Season total** and **Average per round** summary rows; the extras page (one selected milestone) instead shows the full driver-probability table with the actual outcome marked, a top-10 probability bar chart, hit-rate metrics vs the baseline, cumulative-hits and model-confidence line charts (the latter plots `pick_proba`/`actual_proba`), a per-round picks table, milestone points (+15 per hit, same bold summary rows) and feature importance.

Their first cell resolves the repo root (`Path.cwd().parent` when executed from `notebooks/`) so they share the root `cache/` and `data/`. They cover the race pipeline's three target modes (incl. pre-quali direct-only prediction) and the grid pipeline's relaxed pre-quali information set (FP1/FP2 + optional FP3/sprint race), but NOT the extras pipeline, the verbosity levels or the `--models` flag — the notebooks always run both models at the default detail level. **Editing a pipeline `.py` does not update the notebooks — keep both in sync manually**, cell by cell.

## fastf1 gotchas

- Sprint-quali (`SQ`) session results are **empty** in fastf1 3.8.x ("not supported by Ergast"). Derive the sprint quali order from best SQ lap times (existing code in `sprint_quali_features`); fallback = Sprint session `GridPosition`.
- The event schedule is a **static, community-maintained file** fastf1 downloads from `theOehrly/f1schedule` on raw.githubusercontent.com — it is corrected after the fact once the calendar firms up (a round's sprint sessions can appear in it weeks into the season; fastf1's own HTTP cache keeps it only 12h and GitHub serves it with `max-age=300`). Any long-lived process pinning an old copy therefore misclassifies sprint weekends — `predict_extras.is_sprint_weekend` keys on the session names `Sprint`/`Sprint Qualifying`. This bit the hosted app (Singapore 2026 round 17: sprint pole/winner gated off a pre-correction `@st.cache_resource` pin); the fix is the `webapp_common.get_schedule` TTL cache. CLI runs are safe — every run is a fresh process fetching through the short-lived HTTP cache.
- Schedule `Session*DateUtc` values are **tz-naive** despite the name.
- Race results `Position` includes retirees (timing position); DNS rows are NaN. 2026 status values are `Finished`/`Lapped`/`Retired`/`Did not start` — not the old `+1 Lap` format.
- A round only counts as "completed" **3 hours after its race start** (`COMPLETION_BUFFER`), so a run during a live race never caches partial results.
- **fastf1 hard-stops at 500 uncached API calls/hour** (`RateLimitExceededError` raised by its own request limiter; cache-served requests are free, and the pace is capped at 4 calls/s anyway — so the *count* of distinct downloads matters, never the speed; once the hourly budget is blown, subsequent collection crawls until the window rolls over — budget already spent is not recoverable, so batch work right after a rate-limited run can look "hung" while it is really throttled). This is why `data/*.csv` are tracked and kept current by the scheduled `refresh-data` workflow (`scripts/refresh_data.py`, every 6h + on pipeline-code pushes): the app is hosted on Streamlit Community Cloud, whose containers hibernate after 12h without traffic and lose all non-repo disk on restart — without bundled CSVs every cold start bulk-downloads whole seasons and slams into the limit. The bundled `data/team_colors.csv` exists for the same reason: it is the only cold-start-free source of team colors, since even a single extra race-session download for the old live color lookup failed once the process's budget was spent (gray app; see the Team colors note above). `collect_season` treats the limit as a soft stop (fetched rounds are saved; the rest resume on the next run) and takes an optional `rate_limit_wait` (used by the refresh script's `--wait-on-limit`) to sleep and retry instead. The refresh script's `missing_rounds` also detects **stale CSV schemas** (missing required columns → full regeneration, so a pipeline schema change rewrites every bundled season it is run for) and collects the extras kind only for the default years (previous + current) or years that already have an extras CSV — never as a side effect of `--years` on a season that was never bundled. The web-app Season selectbox only offers bundled years (plus the year after the last bundled one as a next-season preview) so visitors can't trigger bulk downloads; the CLI `--season` flag stays unrestricted.

## Determinism

- Models are `HistGradientBoostingRegressor(random_state=42)` (built via `f1_common.make_model`) with fixed data ordering — identical input yields identical backtest metrics, under both profiles (the tuner's candidate sampling is seeded too). If metrics shift after a code change, the change affected the model; it is not noise. Default (`--model fast`) metrics are byte-identical to the pre-profile behavior; the only fast-output change since then is the live training-progress lines (prints only, no metric impact). The defaults of the newer flags are also parity-verified: `--models both` and the default verbosity level reproduce the historical output exactly.
- After touching pipeline code, verify parity by diffing CLI output before/after on a fixed round, e.g. `$PY -u pipelines/predict_race.py --season 2026 --predict-round 15`.
- Prefer a **post-mode round of a bundled season** as the parity target: it resolves from the tracked CSV alone (downloads nothing, deterministic, ~1 min). Capture the before-output *before* editing (`... > /tmp/before.txt 2>&1`), then diff after. Strip fastf1 `WARNING` lines before diffing any run that touched live sessions — which warnings print depends on cache state, not on code.

## Web app verification

```bash
$PY - <<'EOF'
from streamlit.testing.v1 import AppTest
for page, run_key in (("webapp/page_home.py", None),
                      ("webapp/page_race.py", "race_run"),
                      ("webapp/page_quali.py", "grid_run"),
                      ("webapp/page_extras.py", "extras_run")):
    at = AppTest.from_file(page, default_timeout=900)
    at.run()
    assert not at.exception and not at.error, page
    if run_key:  # prediction pages only render after the Run button is pressed
        at.sidebar.button(key=run_key).click()
        at.run()
        assert not at.exception and not at.error, page
    print(page, "OK")
EOF
```

Run from the repo root (the snippet's relative `AppTest.from_file` paths resolve against the cwd of the stdin script); from any other cwd pass absolute paths — the gotcha below applies.

- Prediction pages execute the full backtest + importance when **Run prediction** is pressed (~1-3 min with cached data under the fast profile; the optimized profile takes several times longer). A real browser check is `$PY -m streamlit run app.py --server.headless true` and `curl localhost:8501/healthz`.
- AppTest gotchas (learned the hard way):
  - Press sidebar buttons via `at.sidebar.button(key="race_run").click()` then `at.run()` — elements render in the same run.
  - `selectbox.value` is the raw widget value and `set_value` must be given that same raw value: for label-based options (first-backtest, target, milestone selectboxes) that's the label string; anywhere a `format_func` was used, it's the underlying int. Passing the wrong one raises a confusing `ValueError: list.index(x)`. AppTest.from_file resolves relative paths against the *calling file's* directory — pass absolute paths.
  - Rendered text splits across element lists: `st.markdown` → `at.markdown`, but text rendered with `st.subheader`/`st.success`/`st.info`/`st.caption` does NOT appear in `at.markdown` — assert against `at.subheader`/`at.success`/`at.info`/`at.caption` respectively (checking a section title in `at.markdown` fails even when the page rendered fine).
  - The auto target can **transiently fail right after a quali session whose results Ergast hasn't ingested yet** (the run then reports a clean "Pipeline failed: ... 0 sample(s)" error — no exception; this happens on unmodified HEAD too). When the AppTest run errors like that, select a completed round in the target selectbox instead (the label is `f"Round {rn} — {event} (completed)"`).
  - Chart elements (`st.bar_chart`/`st.altair_chart`) are not exposed on the AppTest element tree — verify charts via absence of exceptions plus the markdown titles around them, not by inspecting chart data. `st.dataframe` tables ARE exposed, though: element type is lowercase `"dataframe"` (not `"DataFrame"` — filtering by the wrong casing silently finds nothing) and `.value` holds the underlying frame with pre-Styler raw values (Probability is a float like `0.1258`, not the formatted `"12.6%"`; Achieved cells are `""`/`"yes"`), so table contents can be asserted directly.
  - AppTest has no theme attached, so `st.context.theme.type` is `None` there and `theme_is_dark` falls back to light mode. To exercise the dark-theme render path end-to-end, monkeypatch `webapp_common.theme_is_dark = lambda: True` before `AppTest.from_file(...)` (import webapp_common first so the pages resolve to the same module instance) — but call `import _bootstrap; _bootstrap.fresh_modules()` (or run any page AppTest once) *before* patching: the page's own `fresh_modules()` stamps each module on first verification and reloads any unstamped module, silently reverting a patch applied to a freshly-imported chain.
