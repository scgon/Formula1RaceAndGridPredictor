## Environment

- **Interpreter**: `/opt/homebrew/Caskroom/miniconda/base/bin/python` (Python 3.14, all deps installed). Do NOT rely on `python3` from PATH — on a fresh shell it can resolve to macOS system Python, which has none of the packages. PyCharm uses this same miniconda SDK.
- **GitHub CLI**: `/opt/homebrew/bin/gh` (authenticated as `scgon`); often not on PATH.
- **Feature worktrees**: new features are usually developed in sibling git worktrees (`git worktree add ../Formula1RaceAndGridPredictor-<name> -b <branch>`). A worktree checks out its own tracked `data/*.csv` (bundled seasons need no re-download) but starts with a **cold fastf1 cache** — `cache/` is gitignored. To share the main checkout's ~1 GB of downloaded sessions, symlink it: `ln -s <main-repo>/cache cache`. Gotcha: a `cache` *symlink* shows as untracked in `git status` (the `cache/` ignore pattern matches directories only) — never `git add -A` over it; drop the symlink when the worktree is retired.
- The pytest suite in `tests/` is the primary verification (deps in `requirements-dev.txt`; see Commands and the Tests section). No lint or typecheck exists. Deeper verification = a full pipeline run or a CLI-output parity diff (pipeline edits).

Page scripts and `webapp_common` self-bootstrap `sys.path` (`webapp/` + `pipelines/`), so they run from the repo root without installation; `app.py` needs no bootstrap (imports only streamlit). `f1_common.BASE_DIR` anchors `cache/` and `data/` at the repo root, shared by pipelines, web app and notebooks no matter where each is executed from.

**Stale-module guard**: Streamlit Community Cloud pulls new commits into the *live* app process without restarting the interpreter, so page scripts re-execute new source while `sys.modules` keeps serving the pre-pull modules (the extras deploy's first push crashed exactly this way: `AttributeError: module 'webapp_common' has no attribute 'run_extras_pipeline'` in a process up since the previous evening). Every page therefore calls `webapp/_bootstrap.fresh_modules()` right after its path bootstrap: it stamps each module's source file (mtime, size) and `importlib.reload`s the whole chain in dependency order on drift (f1_common → the three pipelines → webapp_common), so the app self-heals on the first rerun after a code pull. Reloads keep `@st.cache_resource` hits intact (Streamlit hashes `__module__`+`__qualname__`, not object identity). `_bootstrap.py` itself cannot self-heal — keep it tiny, stdlib-only and stable.

Shared CLI flags: `--season YEAR`, `--predict-round N`, `--next` (next race/quali on the calendar), `--refresh` (re-download season data), `--min-train-rounds N`, `--model {fast,optimized}` (model profile, see below), `--models` (which models the race/quali pipeline trains — `both` (default), `gain`/`anchor`, or `direct`; a pre-quali race target always falls back to `direct`), and the output-level pair `-q/--quiet` + `-v/--verbose` (see the verbosity bullet in Architecture).

- **A bundled season's first run downloads nothing but newly completed rounds** (the season CSVs are tracked); an unbundled season's first run downloads ~45 fastf1 sessions. After that `cache/` and `data/*.csv` make runs take ~3-4 min. A round that fails mid-download is skipped and retried on the next run.
- Always run with `-u`; do not pipe output through `head` — block buffering makes long jobs look stalled.
- Under system load (e.g. a PyCharm Jupyter kernel is running), cap threads: `OMP_NUM_THREADS=4`.
- The optional `.github/workflows/opencode.yml` workflow responds to issue and pull-request comments containing `/oc` or `/opencode`; do not invoke it locally or add its provider secret to the repository.

## Architecture

- `pipelines/f1_common.py` — shared machinery: fastf1 cache setup, UTC/session helpers (`utc_now`, `session_utc`, `completed_rounds`), quali-lap extraction (`best_quali_seconds`, `pole_seconds`), practice features (`practice_features(year, rnd, sessions)`), the season CSV cache (`collect_season`, parameterized by filename/columns/result column/loader, soft stop on the F1 API rate limit, optional `rate_limit_wait` sleep-and-retry), the model factory, `rank_corr`, permutation importance (`importance_scores`/`importance_report`) and the CLI verbosity gating (`VERBOSITY`, `vprint`, `add_verbosity_args`/`apply_verbosity`).
- **Verbosity** — the module-global `f1_common.VERBOSITY` gates CLI output: `-q` (0) trims runs to the backtest summary + final prediction; default (1) is exactly the historical output; `-v` (2) adds live per-round backtest metrics, tuner decisions, importance `±std` and the full extras probability table. Progress prints go through `vprint(level, ...)`; reports gate sections on `VERBOSITY`. The web app never calls `apply_verbosity`, so it always runs at level 1 — its live download/training log depends on the progress prints.
- **Model profiles** (`--model {fast,optimized}`, web-app sidebar) — `fast` (default): `HistGradientBoostingRegressor` with fixed `FAST_PARAMS`. `optimized`: before every fit, `f1_common.tune_hyperparameters` runs a seeded randomized search over `TUNED_SEARCH_SPACE`, scoring candidates by pooled MAE over rolling CV folds (each fold = one training round predicted by the rounds before it; `TUNE_MAX_SPLITS`/`TUNE_STRIDE` pick the folds). `FAST_PARAMS` is always the first candidate and must be beaten by `TUNE_MIN_IMPROVEMENT` (relative MAE) or the tuner returns `None` and the fit falls back to fast values (also covers <2-round training sets, so degenerate models behave identically under both profiles). Tuning inside the backtest only sees rounds before the predicted round. A fold's all-NaN training columns are zeroed for that fold — without that HistGB raises and the round is silently skipped. `train_model` returns the tuned dict; `final_predictions` bundles it as `gain_params`/`anchor_params`/`direct_params` for the "Tuned hyperparameters" display. **The web app hides the optimized profile on Community Cloud** (`webapp_common.on_community_cloud`, fails open to False under AppTest): its multi-minute searches would hog the shared container.
- Two **independent order pipelines** — `predict_race.py` (gain = finish − grid vs direct = absolute finish; baseline = grid order) and `predict_grid.py` (anchor = change vs last quali vs direct; baseline = last-quali persistence). Each owns its FEATURES/targets/feature engineering (`build_features`), sprint handling and round loaders.
  - **Race target modes** (`resolve_target` → (round, mode, event)): `post` reviews a completed round; `pre` predicts after qualifying (grid known — `load_upcoming_round` builds the upcoming frame from quali results); **`prequali`** predicts before qualifying — no grid exists, `load_upcoming_round_prequali` builds the frame from practice entrants (first session with results, else the last completed round's entrants), grid/quali features stay NaN, and `final_predictions(..., models="direct")` runs the **direct model only** (the gain model has no grid to anchor to; HistGB routes the NaN grid at inference down the learned missing-value branch). Auto/`--next`/`--predict-round` all resolve an upcoming round to prequali when its quali hasn't run (with a printed note when no practice has finished either — `practice_done_by`, 2h buffer). **Pre-mode quali-results lag**: the results provider can lag hours behind a session, so a pre target can carry 22 entrant rows with an all-NaN grid — the gain model would filter itself down to zero rows and sklearn would crash ("Found array with 0 sample(s) (shape=(0, 1))" — the shape is the one-hot `team_id` column). `load_upcoming_round_checked` therefore returns (frame, mode) and downgrades such a round to `prequali` with a printed note (both CLI `main()` and the web app's `prepare_features` re-assign `mode` from it, so the web-app bundle renders the direct-only layout with a `grid_note` caption on `page_race`); the frame keeps the quali entry list and falls back to prequali entrants when even that is empty. `predict_round` also raises a clean ValueError on an empty prediction frame as a belt-and-braces guard. The backtest skips grid-less rounds entirely; rounds with an ingested grid keep byte-identical pre behavior.
  - **Grid information set**: FP1/FP2 pace always, plus sprint quali, FP3 (`fp3_*`) and sprint-race results (`sprint_finish`/`sprint_gain`) once those sessions have run — never mandatory (NaN before they happen; `usable_features` drops them only when a training set has none at all). The backtest therefore evaluates the "everything available pre-quali" task.
  - **Web-app API** each pipeline exposes: `backtest_records(features, min_train_rounds, profile, models="both")` → per-round metric dicts (`backtest_report(records, models)` prints them; the record/report split left CLI output unchanged). `final_predictions(features, target, profile, models="both")` → `{gain/anchor, direct, *_model, train, *_features, *_params}` (`final_report` prints; with both models the main frame carries a `direct_pos` column for side-by-side display); a race prequali target passes `models="direct"`. `importance_frame(pred, mode)` → one final model's permutation importance. `models` selects what trains per round (`both`/`gain`/`anchor`/`direct`) and records carry only the trained model's fields. Records also carry web-app-only fields the CLI never prints: `gain_points`/`direct_points` or `anchor_points`/`direct_points` (+15 exact podium slot/pole, +5 wrong slot), `*_top1`/`actual_top1` names and `*_train_rounds`. Gotcha: with both models the grid bundle's `train` frame stays the ANCHOR's training set — the direct set includes round-1 rows with NaN `quali_pos_last`, which would crash the anchor importance target.
  - sklearn's HistGradientBoosting **cannot fit a feature column that is entirely NaN** (`ValueError: window shape cannot be larger than input array shape`, still true in sklearn 1.9.x; round-1 form features and pre-sprint sprint columns are all-NaN). Each pipeline's `train_model` drops those via `usable_features(train)`; `make_model` recomputes the `team_id` categorical index in the reduced list, and `predict_round`/importance reuse the returned list — this is what lets the backtest predict round 2 (trained on round 1 only).
  - A model trained on a **single round (~22 rows) cannot make any tree split** (`min_samples_leaf=20` needs ≥40 rows in a parent), so it predicts a constant and collapses to the baseline order (grid order for race; last-quali order for the grid pipeline, plus `rank(method="first")` tie-breaking by the pre-sort). Race backtest round 2 and quali round 3 are therefore baseline performance, not model skill; the web app flags them via `degenerate_backtest_note`/`degenerate_training_note` (webapp_common), gated on the `*_train_rounds` record fields and the bundle's `train_rounds`.
- `pipelines/predict_extras.py` — the **milestone pipeline**: seven small binary `HistGradientBoostingClassifier`s (one per target in `TARGETS`: pole, winner, podium, first_dnf, fastest_lap, sprint_pole, sprint_win), each with its own feature list — **one runs per invocation** (CLI `--milestone` flag or web-app *Milestone* selectbox, default pole), scoring every candidate row with `predict_proba`; top pick = prediction, compared against a naive baseline (`baseline_pick` sorts by `TARGETS[name]["baseline_sort"]`, NaN last, driver_number tie-break — pole: best season quali form; winner/podium: grid P1; first DNF: most retirements; fastest lap: most FLs then fastest qualifier; sprint pole: best previous sprint-quali form then season quali form; sprint winner: the sprint pole sitter).
  - **Information sets**: the pole model keeps the day-before-quali set (FP1/FP2 → `fp12_*` columns, sprint quali, quali form, points) and never includes the target round's qualifying, so it can also predict before quali runs. The four race milestones (winner, podium, first_dnf, fastest_lap) mirror the race pipeline's pre-race set (grid, FP1–FP3, sprint quali + race, driver/team form, points) plus reliability/milestone history (`driver_dnf_rate_season`, `team_dnf_rate_season`, `driver_wins_before`, `driver_fl_before`, `driver_podiums_before`, …) — all `shift(1)`-derived so a round never sees itself. Sprint models respect sprint-weekend chronology (FP1 → SQ → sprint → GP quali → race): **sprint_pole** uses FP1, quali form and past-sprint history (`sprint_quali_pos_last`, `sprint_quali_form_season`, `sprint_finish_last` — built with a shift over each driver's non-null sprint entries, so weekend N never sees its own results); **sprint_win** may additionally use the target round's SQ result but never the sprint race results or GP quali.
  - **Sprint targets are DERIVED** in `build_features` from the stored `sprint_quali_pos`/`sprint_finish` columns (`sprint_pole = SQ P1`, `sprint_win = sprint P1`) — no CSV schema change, no regeneration. Both train only on sprint rounds (`train_columns` masks) and score the SQ participants (`rows_column="sprint_quali_pos"`); a completed candidate-less round (a non-sprint weekend) is skipped by the backtest and makes `final_predictions` return a "sprint weekends only" error. Training sets are tiny (~5-6 sprint rounds) — degenerate captions and fast-fallback tuner behavior apply.
  - **Own season CSV** `extras_season_{year}.csv`: first_dnf/fastest_lap need race lap data (`race.load(laps=True)`), which the other pipelines never download, so the extras loader re-derives everything itself. Bundled for **2025–2026** only — the web-app season picker gates on `bundled_years("extras")`; keep that gating if coverage changes; the CLI stays unrestricted. First cold collection costs ~25–30 API calls/round (lap data counts against the limit) — expect a rate-limit soft stop mid-season; resume by re-running.
  - **Target definitions**: pole = quali P1; winner = race P1; podium = classified top-3 finish (`finish <= 3`, DERIVED like the sprint targets); a driver retired (`dnf`) iff `finish` is not NaN (DNS rows are NaN) and the status is not Finished-like (`Finished`, `Lapped`, `Disqualified`, `+N Lap(s)` — DSQ completed the race); `first_dnf` = retiree(s) with the fewest completed laps (lap-1 pile-ups tie → multi-hot set, a hit is any of them; hit rates average only over rounds with ≥1 retirement — `dnf_any` marks those); `fastest_lap` = min race `LapTime` (deleted laps filtered).
  - **Pre/prequali modes**: pre requires quali done (the upcoming frame always has a grid), so every `pre_scored` milestone (pole, sprint_pole, sprint_win — decided before the race) is immediately scoreable (`actual_drivers` knows their winners); race milestones show "not known yet" (flags 0 → `actual=[]` → hit `None`). The **pole model additionally has a prequali mode** (`TARGETS["pole"]["prequali"]`): auto/`--next`/`--predict-round` resolve an upcoming round to prequali before its quali runs, with the no-practice-yet note (`practice_done_by`/`_prequali_note`). `target_rows` falls back to all entrants when a prequali-capable milestone meets a round with no quali positions at all; completed candidate-less rounds still return empty. The prequali round rides along as the backtest's last row with NaN hits. Sprint-milestone resolution is sprint-gated (`is_sprint_weekend`, from the schedule's session names "Sprint"/"Sprint Qualifying"): `--next`/`--predict-round` on a non-sprint upcoming round exits with a hint at the next sprint weekend; auto jumps to the next upcoming sprint weekend or reviews the last completed sprint round; the web-app *Target weekend* selectbox lists only sprint weekends for them and offers "Next on the calendar" only while the next upcoming round is one.
  - **Classifiers ≠ regressors**: `CLASSIFIER_FAST_PARAMS` = FAST_PARAMS minus `loss` with `min_samples_leaf=10` (positives are ~1/20 of rows); the tuner is `tune_classifier` (same folds/sampling/min-improvement, scoring pooled **log loss**; single-class folds are skipped; a single-class training set raises `ValueError` → that round records NaN metrics); importance uses `neg_log_loss`. A single-round classifier CAN split, so the extras page uses softer degenerate captions. `backtest_records(..., milestone)`/`final_predictions(..., milestone)` run only the selected target: records carry `hit`/`top3`/`base`, `top1`/`baseline`/`actual` names and `pick_proba`/`actual_proba` (the model's probability for its own pick and the actual driver, charted on the page); `final_predictions` returns a single entry (`pred["name"]` holds the milestone key; an `"error"` key replaces the model when it cannot train). `webapp_common.resolve_target` threads the selected `milestone` into the extras namespace (race/grid ignore it).
- **Streamlit app** (`app.py`, `st.navigation`): `webapp/page_{home,race,quali,extras}.py` are the pages; `webapp_common.py` is app-only glue: `capture_stdout` (nested captures tee into the parent; live-streams into an `st.empty` log element), `run_pipeline`/`run_extras_pipeline` (data load → target resolution → features → backtest → final models → importance, returning a render bundle or `{"error": ...}`; a race prequali target passes `models="direct"` and renders the direct frame as `main` with `imp_main` = None) and UI/table/chart helpers. `page_link` wraps `st.page_link` so pages also run standalone (AppTest).
- Web app execution model — **button-gated**:
  - Changing a widget never starts the pipeline. The sidebar **Run prediction** button executes `run_pipeline` once and stores the bundle in `st.session_state[f"{kind}_result"]` (plus a settings snapshot for the "settings changed since the last run" warning); reruns only render. **Reload season data** refreshes the data layer only; the **Force full re-download** checkbox maps to CLI `--refresh` but takes effect on the next Reload/Run press — checking it alone downloads nothing.

## fastf1 gotchas

- Sprint-quali (`SQ`) session results are **empty** in fastf1 3.8.x ("not supported by Ergast"). Derive the sprint quali order from best SQ lap times (existing code in `sprint_quali_features`); fallback = Sprint session `GridPosition`.
- The event schedule is a **static, community-maintained file** fastf1 downloads from `theOehrly/f1schedule` on raw.githubusercontent.com — corrected after the fact once the calendar firms up (a round's sprint sessions can appear weeks into the season; fastf1's HTTP cache keeps it only 12h). Any long-lived process pinning an old copy misclassifies sprint weekends (`predict_extras.is_sprint_weekend` keys on the session names "Sprint"/"Sprint Qualifying"); this bit the hosted app, and is why `get_schedule` uses the TTL cache. CLI runs are safe — every run is a fresh process through the short-lived HTTP cache.
- Schedule `Session*DateUtc` values are **tz-naive** despite the name.
- Race results `Position` includes retirees (timing position); DNS rows are NaN. 2026 status values are `Finished`/`Lapped`/`Retired`/`Did not start` — not the old `+N Lap` format.
- Session results can carry **glitched `TeamColor` cells** (the literal string `'nan'` for Haas in Abu Dhabi 2021) — `f1_common.season_team_colors` therefore only accepts well-formed hex values; the unfiltered lookup once bundled `#nan` into `data/team_colors.csv` and rendered Haas gray everywhere (found by `tests/test_data_bundle.py`, repaired alongside it).
- A round only counts as "completed" **3 hours after its race start** (`COMPLETION_BUFFER`), so a run during a live race never caches partial results.
- **fastf1 hard-stops at 500 uncached API calls/hour** (`RateLimitExceededError`; cache-served requests are free, the pace is capped at 4 calls/s — the *count* of distinct downloads matters, never the speed; a blown budget crawls until the window rolls over, so batch work right after a rate-limited run can look "hung"). This is why `data/*.csv` are tracked and kept current by the scheduled `refresh-data` workflow (`scripts/refresh_data.py`, every 6h + on pipeline-code pushes): the app is hosted on Streamlit Community Cloud, whose containers hibernate without traffic and lose all non-repo disk on restart — a cold start without bundled CSVs bulk-downloads whole seasons and slams the limit. The bundled `team_colors.csv` exists for the same reason. `collect_season` treats the limit as a soft stop (fetched rounds are saved; the rest resume on the next run) or sleeps/retries with `rate_limit_wait` (`--wait-on-limit`). `refresh_data.missing_rounds` also detects **stale CSV schemas** (missing required columns → full regeneration, so a pipeline schema change rewrites every bundled season it runs for) and collects the extras kind only for the default years or years that already have an extras CSV — never as a side effect of `--years`. The web-app Season selectbox only offers bundled years (plus the year after the last bundled one as a preview) so visitors can't trigger bulk downloads; the CLI `--season` flag stays unrestricted.

## Determinism

- Models are `HistGradientBoostingRegressor(random_state=42)` (via `f1_common.make_model`) with fixed data ordering — identical input yields identical backtest metrics under both profiles (the tuner's candidate sampling is seeded too). If metrics shift after a code change, the change affected the model; it is not noise. Default (`--model fast`) metrics are byte-identical to the pre-profile behavior; the only fast-output change since then is the live training-progress lines (prints only).
- After touching pipeline code, verify parity by diffing CLI output before/after on a fixed round, e.g. `$PY -u pipelines/predict_race.py --season 2026 --predict-round 15`.
- Prefer a **post-mode round of a bundled season** as the parity target: it resolves from the tracked CSV alone (downloads nothing, deterministic, ~1 min). Capture the before-output *before* editing (`... > /tmp/before.txt 2>&1`). Strip fastf1 `WARNING` lines before diffing any run that touched live sessions — which warnings print depends on cache state, not code.

## Web app verification

The permanent AppTest coverage lives in `tests/test_webapp_apptest.py` (homepage render + one full Run per prediction page, pinned to the last completed round so it stays deterministic and offline apart from the schedule fetch). For ad-hoc checks: `AppTest.from_file(<absolute path>, default_timeout=900)` → `at.run()` → press `at.sidebar.button(key="race_run").click()` → `at.run()`; assert `not at.exception and not at.error`.

- Prediction pages execute the full backtest + importance when **Run prediction** is pressed (seconds on Apple Silicon, up to a few minutes on slower hardware under the fast profile; the optimized profile several times longer). A real browser check is `$PY -m streamlit run app.py --server.headless true` and `curl localhost:8501/healthz`.
- AppTest gotchas (learned the hard way):
  - Press sidebar buttons via `at.sidebar.button(key="race_run").click()` then `at.run()` — elements render in the same run.
  - `selectbox.value` is the raw widget value and `set_value` must be given that same raw value: for label-based options (first-backtest, target, milestone selectboxes) that's the label string; anywhere a `format_func` was used, it's the underlying int. Passing the wrong one raises a confusing `ValueError: list.index(x)`. `AppTest.from_file` resolves relative paths against the *calling file's* directory — pass absolute paths.
  - Rendered text splits across element lists: `st.markdown` → `at.markdown`, but text rendered with `st.subheader`/`st.success`/`st.info`/`st.caption` does NOT appear in `at.markdown` — assert against the matching element list instead.
  - The auto target used to fail cleanly right after a quali session whose results Ergast hadn't ingested yet (a "Pipeline failed: ... 0 sample(s)" error); a pre-mode round with no ingested quali results now downgrades to a prequali-style direct-model prediction instead (see the race target modes bullet), so the AppTest auto target renders a prediction even in that window.
  - Chart elements (`st.bar_chart`/`st.altair_chart`) are not exposed on the AppTest element tree — verify charts via absence of exceptions plus the markdown titles around them. `st.dataframe` tables ARE exposed: element type is lowercase `"dataframe"` (not `"DataFrame"` — filtering by the wrong casing silently finds nothing) and `.value` holds the underlying frame with pre-Styler raw values (Probability is a float like `0.1258`, not `"12.6%"`; Achieved cells are `""`/`"yes"`).
  - AppTest has no theme attached, so `theme_is_dark` falls back to light mode. To exercise the dark-theme render path, monkeypatch `webapp_common.theme_is_dark = lambda: True` before `AppTest.from_file(...)` (import webapp_common first) — but run `import _bootstrap; _bootstrap.fresh_modules()` (or any page AppTest) *before* patching: the page's own `fresh_modules()` reloads unstamped modules and would silently revert a patch applied to a freshly-imported chain.
